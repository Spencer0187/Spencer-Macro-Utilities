# Timing compatibility contract

Timing is observable SMU behavior. The Rust parity phase does not collapse the current controller
and worker topology into a single scheduler unless differential traces prove that doing so is
behaviorally identical.

## Current oracle topology

- `MacroRuntime::controllerLoop` polls most macro state on one controller thread. Sleeps performed by
  controller-path macros intentionally stall unrelated polling during that interval.
- One-shot and persistent worker macros created by `MacroRuntime::runWorker` run on independent
  native threads and may overlap each other and the controller.
- Imported scripts execute on independent runtime workers. Coroutines inside one script are resumed
  serially by that script instance.
- Native `InputBackend::pressKey` sleeps between down/up without cancellation.
- Lua `pressKey` uses `ScriptInstance::waitFor` and is cancellation-aware.
- Lua precise waits block efficiently until the final 600 microseconds and then spin the bounded
  tail. The 600us value is an oracle value, not yet a Rust tuning recommendation.

## What tests must prove

Logical tests use a fake monotonic clock and timestamped fake backends. They assert exact action
order and exact requested delays without depending on wall-clock scheduling noise.

Real-clock tests separately measure the platform timing primitive. The existing C++ benchmark sweeps
short waits and evaluates precision/CPU tradeoffs; Rust should retain an equivalent benchmark rather
than making ordinary unit tests flaky.

The first differential trace set must cover:

1. press-key down/delay/up ordering;
2. Wallhop split-delay and 100ms envelope behavior;
3. Speedglitch/ItemClip/WallWalk controller stalls;
4. overlapping one-shot workers;
5. SpamKey and Bunnyhop cancellation boundaries;
6. `FrameDelaysForFps` threshold behavior around the 0.33/0.66 fractional boundaries and 0.008
   epsilon;
7. Lua coarse wait, precise wait, cancellation, sleep-until-cancelled, and coroutine resume order;
8. Lua execution-budget reset after waits/checkpoints;
9. runtime shutdown ordering and held-input/process/network cleanup.

## Automated corpus

`runtime_cases.json` is generated by `smu_runtime_compat_oracle` through
`tools/update_compat_fixtures.py runtime`. The oracle and production runtime share the small pure
helpers in `app/macro_runtime_compat_logic.h`, so the fixture does not carry a second handwritten
copy of the timing arithmetic or PressKey worker sequence.

The current automated Rust slice freezes all integer FPS inputs from 0 through 1000, all rising-edge
states, PressKey delay clamping / trigger-release / cancellation ordering, the full boolean
Speedglitch edge/toggle matrix, Freeze hold/toggle/wheel behavior and timeout recovery, ItemDesync
slot clamping plus its four direct key transitions, ItemClip toggle/hold state with controller-lane
half-delay waits, and WallWalk frame-delay/mouse/tail-delay ordering. Freeze, Speedglitch, ItemClip,
and WallWalk waits remain controller-lane stalls; PressKey waits remain independent worker-lane
waits. Freeze fixtures include failed suspend/resume attempts and post-timeout re-suspension. The
production Speedglitch path deliberately reads its second strength value only after the first sleep.
WallWalk snapshots both movement strengths before its first move, but reads the microsecond tail
delay only after the first frame wait and second move; the trace freezes that distinction. Wallhop
runs entirely on a generic worker lane; its delay/bonus boundaries, optional jump/flick behavior,
and 100 ms release target are differential-tested without advancing the controller clock. Walless
LHJ also stays on a generic worker lane for its full 645 ms sequence. Its PID vector is snapshotted
before spawn, while side/zoom/shift settings are deliberately re-read inside the worker at their
historical action/release points; the fixture includes settings changing between those reads. HHJ
likewise snapshots only its PID vector: auto-toggle/key/time settings, freeze-delay settings,
zoom/shift settings, and `HHJLength` are read at their original worker-time sites. Repeated reads can
observe different values, including releasing different auto/shift keys than were pressed and leaving
`isHHJ` active when the later length check changes to zero. FloorBounce also snapshots only its PID
vector, then runs an uncancelled generic-worker sequence with 521/72/72/72 ms base waits. Its HHJ
flag/delays/shift key are read later inside the worker, and distinct rising edges may overlap because
there is no worker-active guard. Bunnyhop uses its dedicated long-lived worker semantics: physical
trigger classification distinguishes wheel/none, mouse-backend, and keyboard-latch sources; the
loop-head guard checks runtime/macro/binding/section state, while the mid-cycle cancellation check
only rechecks runtime/target-loop state. Its bound output key and half-delay are snapshotted per
iteration, and cancellation after the first half always releases the key before exiting. Freeze's
process-control layer is also differential-tested: partial suspend/resume success counts as overall
success, resume never refreshes targets, all-failed suspension refreshes and retries only when the
ordered PID vector changes, duplicate PIDs are not deduplicated, and partial resume success clears
the entire frozen-PID snapshot exactly as the current C++ implementation does.

Regenerate after an intentional C++ timing compatibility change:

```sh
cmake --build build --target smu_runtime_compat_oracle
python3 tools/update_compat_fixtures.py runtime
cargo test --manifest-path rust/Cargo.toml -p smu-runtime
```

## Compatibility versus later fixes

Some current behavior is awkward or racy. For example, native one-shot workers can sleep through
shutdown and the current stop order can unfreeze a process before every native worker has joined.
Those are recorded as oracle behavior first. A later safety change should have its own test and
release note rather than being smuggled into the language rewrite.
